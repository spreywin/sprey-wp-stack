Sprey platform architecture and roadmap.

CORE PRINCIPLES

Infrastructure before complexity.

01

Non-custodial payments

Sprey infrastructure must not become the custodian of customer funds. BTCPay is used for payment orchestration and notifications while wallet control remains with the customer.

02

Separate responsibilities

The website, payment infrastructure, RPC services, VPN nodes, monitoring and documentation are separate operational units. A failure in one service should not unnecessarily expose or stop the others.

03

Minimal public perimeter

Only required edge services are exposed publicly. Databases and administration utilities stay on private Docker networks or localhost-only interfaces.

04

Reproducible stacks

Deployments should be represented as versioned Docker Compose stacks and documented procedures instead of undocumented server-panel state.

05

Automation first

Provisioning, billing, access delivery, health checks and routine operations should require as little manual support as practical.

06

Static docs and fallback

Documentation and outage communication should remain available independently from the main application VPS.

PRODUCT MAP

Products are not stacks.

P1

Sprey Processing

Hosted BTCPay-based payment infrastructure. Customer wallets remain under customer control. External Lightning nodes may be connected; operating customer funds on Sprey-owned Lightning nodes is not part of the core model.

P2

Sprey RPC

Planned RPC/eRPC service aggregating stable providers for TRON and EVM networks with API keys, health monitoring and plan-based billing.

P3

Sprey VPN

Planned privacy service with isolated VPN traffic nodes and crypto billing. VPN traffic infrastructure stays separate from the web store and payment server.

Product defines what a customer buys. Stack defines how an infrastructure component is deployed and operated.

EDGE & RESILIENCE

Cloudflare protects the website without pretending static HTML is WooCommerce.

Primary origin

The WordPress VPS remains the live origin for the Store. Dynamic routes such as cart, checkout, account and WordPress administration must not be cached as static content.

Static outage origin

A Cloudflare Pages project may provide a maintenance/outage page when the primary origin is unavailable.

Failover boundary

The static fallback communicates the outage only. It does not replace WooCommerce checkout, sessions or authenticated customer functionality.
